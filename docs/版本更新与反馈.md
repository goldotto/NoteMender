# 程序更新与邮件反馈

## 用户操作

顶部“版本与更新”可查看当前版本、构建编号、内置更新说明及本机更新记录。默认启动及每6小时检查一次，只检查，不自动下载或安装。关闭开关后仍可手动检查。

“下载更新”只下载程序文件，不重新下载已安装的模型、Python 或显卡组件。验证完成后点击“安装并重启”。所有打开页面必须完成保存；请先提交或清空连续写入队列，结束识别和组件安装。保存失败、其他页面未响应、文件被修改或空间不足时不会开始替换。下载可以取消，重试时在来源支持的情况下续传。

更新恢复工程、候选、未采用歌词、原音引用和当前试听位置；暂停状态恢复，不自动开始播放。浏览器撤销栈不跨重启保存，请在更新前确认当前编辑结果。当前程序目录中的模型、组件配置、导出文件和插件不被程序更新覆盖。更新失败会保留恢复副本并尝试回退；遇到关机或进程中断，重新运行 Start-NoteMender.cmd 会先处理未完成更新。

开发源码目录不提供直接覆盖安装。无法取得可信更新清单时显示“检查失败”，不会声称已经是最新。默认读取 CNB 公开仓库 updates/index.json 中的签名清单，失败时尝试 GitHub。仅上传安装包或提交源码不会产生更新提示；必须先上传并验证更新附件，再发布签名索引。

“问题反馈”中填写问题与复现步骤，生成报告后可以直接修改预览。可取消包含运行日志，重新生成预览。“打开邮件发送”准备发往 **goldotto@proton.me** 的邮件；最后需要你在自己的邮件软件中确认发送。

完整报告请复制到正文或下载 TXT 后附加。没有邮件软件时，可以复制邮箱并使用网页邮箱。程序不能判断邮件是否送达，不会显示“已发送”。不自动上传音频、工程、歌词、截图或凭据。发送前仍请检查自己填写的文字。

## 维护者：首次发布与后续更新

版本元数据以 `public/build-info.json` 为准；发布构建工具会为程序包生成 portable 分发标识。构建编号为严格递增整数，同一个 demo 标签下也不得复用。源码默认为 development，防止覆盖开发文件。

客户端信任 `public/update-trust.json` 的 Ed25519 公钥。签名私钥独立存放，**不得公开或放入程序包**。将其另行备份；丢失后不能使用原公钥签发更新。不要为解决签名失败而关闭验证或替换已分发客户端的信任标记。

1. 完成源码修改、针对性检查及离线构建；更新 RELEASE_NOTES.md。保留 public-files.json 白名单，检查最终包隐私。
2. 运行 `node scripts/package-update.mjs <D盘全新输出目录> <D盘私钥文件> <新构建编号> [上一构建签名清单]`。先预留构建号，打包中断后也不复用这个号。发布到 CNB 时传入镜像配置，主地址使用 CNB 实际上传的更新 ZIP 地址；不要声明未上传的 GitHub 镜像。程序更新包不包含 runtime、exports、插件和 node_modules；浏览器运行依赖已经随离线构建进入 public/vendor。
3. 工具生成专用 Windows 更新 ZIP、NoteMender-update.json 和 installation-receipt.json。最后一份是供同一构建的初次便携安装包使用的签名安装凭据，放在该安装包的 runtime/updates/installed.json。必须使用相同文件字节与构建信息，不能仅给旧程序补一个凭据。
4. 老版分发包没有更新功能或安装凭据，必须先手动安装一次带更新器的新基础版。不能宣称旧版能直接在线升级。
5. 将 ZIP 与 NoteMender-update.json 上传到对应 Release，先保留旧附件。运行 `node scripts/verify-update-release.mjs <输出目录/NoteMender-update.json>`，它实际下载公开附件，验证哈希与公开签名清单；通过后才生成 index.json。
6. **最后**将通过验证的 index.json 放到 CNB 仓库 main 分支 updates/index.json。GitHub 备用 Release 查询识别固定名称 NoteMender-update.json；同一标签更新时先上传 ZIP，替换清单，最后提交索引。
7. 从已分发的上一构建实际升级，核对原端口、工作恢复和回退。模拟测试不能代替真实公开下载验收。

更新程序使用持久事务记录、完整程序文件备份和有界历史。不要手动清理正在安装的 runtime/updates 目录。开发与故障测试应当使用独立的 D 盘小型模拟安装目录；不要拿真实个人工程做故障注入。

同一程序目录仅允许一个服务实例，避免两个端口的服务互相覆盖程序文件。成功后保留最近一次备份；清理旧更新缓存时，只清理可验证的更新文件，未知文件保留。恢复文件缺失时停止启动并提示，不跳过未完成事务。

### 签名材料备份

将签名私钥、同目录的 issued-builds.json 与对应公钥作为一组，备份到独立的加密存储或离线介质；源码和发布附件只放公钥。不要通过聊天、邮件或问题报告传递私钥。构建签发有独占锁；发生中断时先检查签发记录和现有附件，确定原进程已退出，再人工处理遗留锁。无法核实历史构建时，不重用旧号。签发记录损坏会停止打包，不能靠清空记录继续发布。

## 失败处理

- 网络、限流或签名失败：继续使用现版，稍后重试或通过 GitHub 发布页手动下载。
- 文件已修改或未知文件冲突：另存新版到新目录，不能绕过检查覆盖。
- 页面未完成保存：先处理未提交内容，关闭重复页面，再重新准备；无法确认安全时取消安装。
- 重启或恢复失败：保留 runtime/updates 的事务和恢复文件，重新启动并导出问题报告。不要直接删除唯一回退副本。
- 邮件没有打开：复制完整报告、邮箱，使用网页邮箱发送；程序不需要邮箱密码或授权码。

### CNB 旧版迁移

构建 2026102101 及更早版本尚不识别 CNB 下载域名。首次迁移请先保存工程、候选和原音，再从 CNB 或 GitHub 当前 demo.7 发行页下载新安装包（构建 2026102202 或以后）。关闭旧程序，安装到新的空目录，在组件管理中指定旧目录复用模型与环境；旧目录继续保留。安装器不会直接覆盖已有程序。继续使用原端口（默认 4347），保持浏览器保存来源一致，再打开保存的工程并核对原音。不要为迁移删除 runtime 或原工程。开发源码目录继续直接调试源码，不通过在线更新覆盖。

CNB 使用公开原始文件入口与发行附件；客户端仅允许 cnb.cool、asset.cnb.cool 等已核验域名，每次跳转重新检查。签名和哈希是最终完整性依据，不因镜像切换而关闭。发布索引之前必须通过公开下载门禁，并从旧安装目录测试升级及回退。
